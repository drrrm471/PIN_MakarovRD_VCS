## МОДУЛЬ 3. КОМАНДНАЯ РАБОТА И УГЛУБЛЁННЫЕ ТЕХНИКИ (Темы 7–9)

### Тема 7. Стратегии ветвления в команде. Git Flow vs GitLab Flow.

| **Лекции (2 часа)** | **Лабораторные работы (4 часа)** | **Результат обучения** |
|:---|:---|:---|
| **1. Git Flow:**<br>— Постоянные ветки: `main`, `develop`.<br>— Вспомогательные ветки: `feature/*`, `release/*`, `hotfix/*`.<br>— Порядок работы: создание feature → слияние в develop → релизная ветка → main.<br>— Преимущества: структурированность, контроль релизов.<br>— Недостатки: сложность, много веток.<br>**2. GitLab Flow:**<br>— Модель: `main` + feature-ветки + ветки окружений.<br>— Разделение на окружения: staging, production.<br>— Преимущества: простота, интеграция с CI/CD.<br>— Особенности GitLab Flow в GitLab:<br>  - Автоматический деплой через CI/CD.<br>  - Environment-специфичные правила.<br>**3. Trunk-based Development:**<br>— Одна основная ветка `main`.<br>— Короткоживущие feature-ветки (1-2 дня).<br>— Частое слияние, feature-флаги.<br>**4. Выбор стратегии:**<br>— Критерии выбора: размер команды, частота релизов, тип проекта.<br>— Гибридные подходы. | **Реализация различных стратегий ветвления.**<br><br>**Часть 1 (2 часа):**<br>— Реализация Git Flow в учебном проекте:<br>  - Создание веток `develop`, `feature/login`, `feature/registration`.<br>  - Слияние фич в `develop`.<br>  - Создание релизной ветки `release/v1.0`.<br>  - Исправление багов в релизе.<br>  - Слияние релиза в `main` и `develop`.<br>— Использование Merge Request для каждого слияния.<br><br>**Часть 2 (2 часа):**<br>— Реализация GitLab Flow:<br>  - Создание feature-веток от `main`.<br>  - Добавление CI/CD для деплоя на staging и production.<br>  - Работа через Merge Request с требованием CI/CD.<br>— Сравнение двух подходов:<br>  - Оценка сложности.<br>  - Количество конфликтов.<br>  - Время на управление ветками.<br>— Обсуждение выбора стратегии для разных типов проектов. | Студент знает основные стратегии ветвления (Git Flow, GitLab Flow) и умеет применять их на практике. Понимает преимущества и недостатки каждой модели. Может аргументированно выбирать стратегию для конкретного проекта. Интегрирует CI/CD в процесс ветвления. |

## ФОНД ОЦЕНОЧНЫХ СРЕДСТВ (Критерии оценивания лабораторных работ)

| Оценка | Уровень выполнения | Описание |
|:---:|:---|:---|
| **«Отлично» (5)** | Высокий | Лабораторная работа выполнена полностью и в срок. Все команды Git применены корректно, сообщения коммитов осмысленные. Студент демонстрирует глубокое понимание процессов ветвления и слияния, умеет разрешать сложные конфликты. История репозитория чистая и структурированная. Настроен CI/CD пайплайн (если это предусмотрено заданием). Студент может объяснить любую операцию и обосновать выбор стратегии работы. Владеет дополнительными инструментами (LFS, submodules, Container Registry). |
| **«Хорошо» (4)** | Продвинутый | Лабораторная работа выполнена полностью. Основные команды Git используются корректно, но есть небольшие недочёты (например, неинформативные сообщения коммитов, отсутствие тегов). Студент понимает базовые принципы, но может затрудниться с объяснением сложных сценариев (rebase, конфликты). CI/CD настроен с помощью преподавателя. |
| **«Удовлетворительно» (3)** | Базовый | Лабораторная работа выполнена, основные операции Git работают. Есть ошибки в работе с ветками или разрешении конфликтов. История коммитов неструктурированная. Студент может выполнить базовые команды, но не понимает всех принципов работы Git. CI/CD не настроен. |
| **«Неудовлетворительно» (2)** | Ниже базового | Лабораторная работа не выполнена или выполнена с критическими ошибками (репозиторий не работает, коммиты отсутствуют, студент не может выполнить базовые команды Git). Студент не понимает принципов работы систем контроля версий. |

## ДОПОЛНИТЕЛЬНЫЕ МАТЕРИАЛЫ ДЛЯ ПРЕПОДАВАТЕЛЯ

### Рекомендации по использованию GitLab в учебном процессе:

1. **Регистрация студентов** — рекомендуется создать группу на gitlab.com или использовать развернутый инстанс GitLab (при наличии).
2. **Шаблоны проектов** — подготовить шаблонные репозитории с настроенным `.gitignore`, базовым `.gitlab-ci.yml` и структурой README.
3. **Демо-репозиторий** — создать репозиторий с примерами всех изучаемых сценариев (коммиты, ветки, конфликты, CI/CD).
4. **Проверка заданий** — использовать Merge Request для приёма лабораторных работ: студент создаёт MR, преподаватель ревьюит и оставляет комментарии.
5. **CI/CD для проверки** — настроить автоматическую проверку форматирования или тестов в пайплайне для автоматизированной оценки.

### Инструменты GitLab для преподавателя:
- **GitLab Issues** — для постановки задач студентам.
- **GitLab Project Boards** — для визуализации прогресса.
- **GitLab Pages** — для публикации результатов проектов.
- **GitLab CI/CD** — для автоматической проверки работ.
