## 3. ТЕОРЕТИЧЕСКОЕ ВВЕДЕНИЕ

### 3.1. Сравнение стратегий ветвления

| Стратегия | Описание | Сложность | Релизный цикл | Применение |
|:---|:---|:---|:---|:---|
| **Git Flow** | Разветвлённая модель с постоянными ветками `main`, `develop` и вспомогательными `feature/*`, `release/*`, `hotfix/*` | Высокая | Плановые релизы с версионированием | Крупные проекты с фиксированными релизами |
| **GitLab Flow** | Упрощённая модель с `main` и feature-ветками + ветками окружений (`staging`, `production`) | Средняя | Непрерывная доставка | Проекты с частыми релизами и DevOps-практиками |
| **Trunk-based** | Минималистичная модель: одна основная ветка `main` + короткоживущие feature-ветки | Низкая | Непрерывный деплой | Стартапы, CI/CD-зрелые команды |

### 3.2. Git Flow (детально)

**Git Flow** — одна из самых популярных моделей ветвления, предложенная Винсентом Дриссеном .

```
main
  └── develop
        ├── feature/user-auth
        ├── feature/payment
        ├── release/v1.0.0
        └── hotfix/1.0.1
```

**Основные ветки (постоянные):**
- `main` — содержит готовый к релизу код (production-ready).
- `develop` — содержит код для следующего релиза.

**Вспомогательные ветки (временные):**
- `feature/*` — для разработки новых функций (ответвляется от `develop`, сливается в `develop`).
- `release/*` — для подготовки релиза (ответвляется от `develop`, сливается в `main` и `develop`).
- `hotfix/*` — для срочных исправлений в production (ответвляется от `main`, сливается в `main` и `develop`).

### 3.3. GitLab Flow

**GitLab Flow** — более простая модель, которая объединяет преимущества Git Flow и современные DevOps-практики .

```
main
  ├── feature/user-auth
  ├── feature/payment
  ├── staging    (ветка окружения)
  └── production (ветка окружения)
```

**Особенности GitLab Flow:**
- Только одна постоянная ветка — `main`.
- Feature-ветки создаются от `main` и сливаются обратно через Merge Request.
- Ветки окружений (`staging`, `production`) являются обычными ветками, на которые автоматически деплоится код.
- Используются environment-ветки для разграничения окружений.

### 3.4. Trunk-based Development

**Trunk-based Development** — самая простая модель с минимальным количеством веток .

```
main
  ├── feature/short-lived-1 (до 2 дней)
  ├── feature/short-lived-2
  └── feature/short-lived-3
```

**Особенности Trunk-based:**
- Единственная основная ветка — `main`.
- Feature-ветки существуют не более 1-2 дней.
- Частые слияния в `main` (несколько раз в день).
- Использование feature-флагов для скрытия незавершённых функций.
- Автоматический деплой после каждого слияния.

## 4. ПОШАГОВАЯ ИНСТРУКЦИЯ

### Часть 1 (2 часа) — Реализация Git Flow

#### Шаг 1. Создание проекта на GitLab

```bash
# Создание нового проекта на GitLab
# Название: gitflow-lab

git clone git@gitlab.com:username/gitflow-lab.git
cd gitflow-lab

echo "# Git Flow Lab" > README.md
echo "Демонстрация стратегии Git Flow" >> README.md

git add README.md
git commit -m "docs: initial commit"
git push origin main
```

#### Шаг 2. Создание ветки develop

```bash
# Создание develop от main
git checkout -b develop
git push origin develop

# Настройка защиты веток на GitLab
# Settings → Repository → Protected Branches
# - main: Allowed to merge (Maintainers), Allowed to push (No one)
# - develop: Allowed to merge (Developers + Maintainers), Allowed to push (Developers + Maintainers)
```

#### Шаг 3. Создание feature-ветки и разработка

```bash
# Создание feature-ветки от develop
git checkout develop
git checkout -b feature/user-authentication

# Создание кода
cat > auth.py << 'EOF'
#!/usr/bin/env python3
def login(username, password):
    if username == "admin" and password == "secret":
        return {"status": "success", "token": "fake-jwt-token"}
    return {"status": "error", "message": "Invalid credentials"}

def logout(session_id):
    return {"status": "success", "message": "Logged out"}

def register(username, password, email):
    return {"status": "success", "message": "User registered"}
EOF

git add auth.py
git commit -m "feat: add user authentication module"
git push origin feature/user-authentication
```

#### Шаг 4. Создание Merge Request и слияние в develop

1. Перейдите в GitLab → **Merge Requests** → **New merge request**.
2. Source: `feature/user-authentication` → Target: `develop`.
3. Добавьте описание и создайте MR.
4. Выполните слияние.

#### Шаг 5. Создание релизной ветки

```bash
# Создание релизной ветки от develop
git checkout develop
git pull origin develop
git checkout -b release/v1.0.0

# Подготовка релиза (обновление версии, документации)
echo "VERSION = '1.0.0'" > version.py
git add version.py
git commit -m "chore(release): bump version to 1.0.0"
git push origin release/v1.0.0
```

#### Шаг 6. Слияние релизной ветки в main и develop

```bash
# Слияние в main
git checkout main
git pull origin main
git merge release/v1.0.0
git push origin main

# Создание тега релиза
git tag -a v1.0.0 -m "Release v1.0.0"
git push origin v1.0.0

# Слияние в develop
git checkout develop
git merge release/v1.0.0
git push origin develop
```

#### Шаг 7. Создание hotfix'а

```bash
# Обнаружен критический баг в production
git checkout main
git checkout -b hotfix/critical-bug

# Исправление
cat > fix.py << 'EOF'
print("Critical bug fixed")
EOF

git add fix.py
git commit -m "fix: resolve critical authentication bug"
git push origin hotfix/critical-bug

# Слияние hotfix в main и develop
git checkout main
git merge hotfix/critical-bug
git tag -a v1.0.1 -m "Hotfix v1.0.1"
git push origin main --tags

git checkout develop
git merge hotfix/critical-bug
git push origin develop
```

### Часть 2 (2 часа) — Реализация GitLab Flow

#### Шаг 8. Создание проекта для GitLab Flow

```bash
# Создание нового проекта на GitLab
# Название: gitlabflow-lab

git clone git@gitlab.com:username/gitlabflow-lab.git
cd gitlabflow-lab

echo "# GitLab Flow Lab" > README.md
echo "Демонстрация стратегии GitLab Flow" >> README.md
echo "" >> README.md
echo "## Окружения" >> README.md
echo "- `main` — основная ветка" >> README.md
echo "- `staging` — тестовое окружение" >> README.md
echo "- `production` — боевое окружение" >> README.md

git add README.md
git commit -m "docs: initial commit"
git push origin main
```

#### Шаг 9. Создание feature-ветки с CI/CD

```bash
# Создание feature-ветки от main
git checkout -b feature/add-calculator

# Создание кода
cat > calc.py << 'EOF'
#!/usr/bin/env python3
class Calculator:
    def add(self, a, b):
        return a + b

    def subtract(self, a, b):
        return a - b

    def multiply(self, a, b):
        return a * b

    def divide(self, a, b):
        if b == 0:
            raise ValueError("Cannot divide by zero")
        return a / b
EOF

git add calc.py
git commit -m "feat: add calculator module"
git push origin feature/add-calculator
```

#### Шаг 10. Создание Merge Request

1. Перейдите в GitLab → **Merge Requests** → **New merge request**.
2. Source: `feature/add-calculator` → Target: `main`.
3. Добавьте описание и создайте MR.
4. Выполните слияние.

#### Шаг 11. Настройка окружений в GitLab

В `.gitlab-ci.yml` добавьте:

```yaml
stages:
  - test
  - deploy

test:
  stage: test
  image: python:3.11-slim
  script:
    - echo "Running tests..."
    - python -c "from calc import Calculator; c=Calculator(); assert c.add(1,2)==3"
    - echo "Tests passed!"
  only:
    - merge_requests

deploy_staging:
  stage: deploy
  script:
    - echo "Deploying to Staging..."
    - # Команда деплоя на staging
  environment:
    name: staging
    url: https://staging.example.com
  only:
    - main

deploy_production:
  stage: deploy
  script:
    - echo "Deploying to Production..."
  environment:
    name: production
    url: https://production.example.com
  when: manual
  only:
    - main
```

#### Шаг 12. Деплой через окружения

1. В GitLab → **CI/CD** → **Pipelines** → запустите пайплайн.
2. После успешного деплоя на staging — перейдите в **Deployments** → **Environments** → `staging`.
3. Нажмите **"Deploy"** для production (ручной деплой).

### Часть 3 — Сравнение стратегий

#### Шаг 13. Создание сравнительной таблицы в проекте

```bash
cat > COMPARISON.md << 'EOF'
# Сравнение стратегий ветвления

| Критерий | Git Flow | GitLab Flow | Trunk-based |
|:---|:---|:---|:---|
| **Сложность** | Высокая | Средняя | Низкая |
| **Количество веток** | Много | Среднее | Мало |
| **Релизный цикл** | Плановый | Непрерывный | Непрерывный |
| **Поддержка hotfix'ов** | ✅ Отличная | ⚠️ Через feature-ветки | ⚠️ Через cherry-pick |
| **Feature-флаги** | ❌ | ⚠️ | ✅ |
| **CI/CD интеграция** | ⚠️ Средняя | ✅ Отличная | ✅ Отличная |
| **Когда использовать** | Крупные проекты с версионированием | Проекты с частыми релизами | Стартапы, DevOps-команды |

## Рекомендации по выбору

1. **Git Flow** — для проектов с долгосрочным планированием и фиксированными релизами.
2. **GitLab Flow** — для проектов с частыми релизами и активным использованием CI/CD.
3. **Trunk-based** — для стартапов и команд с высокой зрелостью CI/CD.
EOF

git add COMPARISON.md
git commit -m "docs: add strategies comparison"
git push origin main
```

## 5. ТАБЛИЦА СРАВНЕНИЯ СТРАТЕГИЙ

| Критерий | Git Flow | GitLab Flow | Trunk-based |
|:---|:---|:---|:---|
| **Основная ветка** | `main` + `develop` | `main` | `main` |
| **Feature-ветки** | От `develop` | От `main` | От `main` (очень короткие) |
| **Релизные ветки** | `release/*` | Нет (используются теги) | Нет |
| **Hotfix-ветки** | `hotfix/*` | Нет (feature-ветка) | Нет (fix в main) |
| **Деплой на staging** | Из `develop` | Из ветки `staging` | Из `main` (с feature-флагами) |
| **Деплой на production** | Из `main` | Из ветки `production` | Из `main` |
| **История** | Сложная, много merge-коммитов | Линейная | Очень линейная |
| **Сложность внедрения** | Высокая | Средняя | Низкая |
| **Подходит для** | Крупные продукты с релизами | Веб-приложения, SaaS | Стартапы, микросервисы |

## 7. ЧАСТЫЕ ОШИБКИ И ИХ РЕШЕНИЕ

| Ошибка | Причина | Решение |
|:---|:---|:---|
| `Merge conflict` в `develop` | Много feature-веток с изменениями в одних файлах | Чаще сливайте feature-ветки в develop |
| Забыли слить release в develop | Релизная ветка не полностью синхронизирована | Выполните `git merge release/... develop` |
| Hotfix не слит в develop | Исправление работает только в main | Не забудьте слить hotfix во все ветки |
| Бесконечные конфликты при rebase | Слишком старая ветка | Чаще обновляйте feature-ветки из основной |
| CI/CD падает на main | Изменения не протестированы в feature-ветке | Требуйте прохождения CI в MR |
| Много долгоживущих веток | Нарушение принципов Trunk-based | Ограничьте время жизни feature-веток |

## 8. ВЫБОР СТРАТЕГИИ: РЕКОМЕНДАЦИИ

### Выбирайте Git Flow, если:
- Команда > 10 разработчиков.
- Проект имеет фиксированные релизные циклы (например, раз в квартал).
- Требуется строгое версионирование (семантическое).
- Есть отдельная команда тестирования, работающая с релизными кандидатами.

### Выбирайте GitLab Flow, если:
- Команда 3-10 разработчиков.
- Частые релизы (еженедельно или чаще).
- Активно используется CI/CD.
- Нужны отдельные окружения для тестирования.
- Проект — веб-приложение или SaaS-сервис.

### Выбирайте Trunk-based, если:
- Команда < 5 разработчиков.
- Непрерывный деплой (несколько раз в день).
- Используются feature-флаги.
- Команда опытная, с высокой культурой CI/CD.
- Микросервисная архитектура.
