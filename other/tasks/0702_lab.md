## 3. ТЕОРЕТИЧЕСКОЕ ВВЕДЕНИЕ

### 3.1. Окружения (Environments) в GitLab

Окружения в GitLab CI/CD предоставляют изолированные этапы для разработки, тестирования и эксплуатации приложений . Они позволяют безопасно разрабатывать функции, проводить тщательное тестирование перед выпуском и иметь чёткое представление о том, какая версия где запущена .

**Типы окружений:**

| Тип | Описание | Применение |
|:---|:---|:---|
| **Статические (Static)** | Определяются в .gitlab-ci.yml с фиксированными URL и конфигурацией | Staging, Production |
| **Динамические (Dynamic)** | Автоматически генерируются для каждого запуска пайплайна | Ветки разработки |
| **Review Apps** | Временные окружения для каждого Merge Request | QA, демонстрации, ревью |
| **Защищённые (Protected)** | Требуют утверждения перед деплоем | Production  |

Окружение представляет собой метку, обозначающую цель развертывания (например, `staging`, `production`), а деплой — это экземпляр вашего кода, отправленный в это окружение. GitLab отслеживает каждый деплой как запись, что позволяет просматривать историю и выполнять откат .

### 3.2. Review Apps

Review Apps — это временные тестовые окружения, которые автоматически создаются для каждой ветки или Merge Request . Они позволяют разработчикам и заинтересованным лицам просматривать и тестировать изменения в изолированной среде до их слияния с основной веткой .

**Преимущества Review Apps:** 
- Устраняют необходимость локальной настройки для тестирования изменений.
- Обеспечивают единообразные окружения для всех членов команды.
- Позволяют заинтересованным лицам просматривать изменения по URL.
- Ускоряют обратную связь до того, как изменения попадут в production.

**Рабочий процесс Review Apps:** 
1. Создание ветки и Merge Request.
2. Запуск пайплайна.
3. Развертывание приложения в динамическое окружение `review/название-ветки`.
4. Появление ссылки "View app" в Merge Request.
5. После слияния или закрытия MR — автоматическое удаление окружения.

### 3.3. Стратегии развертывания

GitLab поддерживает различные стратегии непрерывного развертывания :

| Стратегия | Настройка | Описание |
|:---|:---|:---|
| **Continuous Deployment** | Автоматический деплой в production | Каждый успешный пайплайн на main разворачивается в production |
| **Continuous Delivery** | Автоматический деплой в staging, ручной в production | Изменения тестируются на staging, в production — по кнопке |
| **Incremental Rollouts** | Поэтапный выпуск | Развертывание с задержками для мониторинга  |

## 4. ПОШАГОВАЯ ИНСТРУКЦИЯ

### Часть 1 (2 часа) — Создание приложения и настройка статических окружений

#### Шаг 1. Создание проекта на GitLab

1. Войдите в GitLab.
2. Нажмите **"New project"** → **"Create blank project"**.
3. Название: `environments-lab`.
4. Уровень доступа: **"Private"**.
5. Нажмите **"Create project"**.

#### Шаг 2. Клонирование репозитория

```bash
git clone git@gitlab.com:username/environments-lab.git
cd environments-lab
```

#### Шаг 3. Создание простого веб-приложения (Node.js + Express)

```bash
cat > package.json << 'EOF'
{
  "name": "environments-lab",
  "version": "1.0.0",
  "scripts": {
    "start": "node index.js",
    "test": "node test.js"
  },
  "dependencies": {
    "express": "^4.18.2"
  }
}
EOF

cat > index.js << 'EOF'
const express = require('express');
const app = express();
const port = process.env.PORT || 3000;

app.get('/', (req, res) => {
  res.json({
    message: 'Hello from GitLab Environments!',
    environment: process.env.ENVIRONMENT || 'development',
    version: process.env.APP_VERSION || '1.0.0'
  });
});

app.get('/health', (req, res) => {
  res.status(200).json({ status: 'healthy' });
});

app.listen(port, () => {
  console.log(`App running on port ${port}`);
});
EOF

cat > test.js << 'EOF'
const http = require('http');

console.log('Running tests...');
// Простой тест для демонстрации
console.log('✅ All tests passed!');
EOF
```

#### Шаг 4. Создание Dockerfile

```bash
cat > Dockerfile << 'EOF'
FROM node:18-alpine

WORKDIR /app

COPY package*.json ./
RUN npm install --production

COPY . .

EXPOSE 3000

CMD ["npm", "start"]
EOF
```

#### Шаг 5. Базовый `.gitlab-ci.yml` со статическими окружениями

```bash
cat > .gitlab-ci.yml << 'EOF'
stages:
  - test
  - build
  - deploy

variables:
  APP_VERSION: "1.0.0"
  CI_REGISTRY_IMAGE: $CI_REGISTRY_IMAGE

# --- Стадия: Тестирование ---
test:
  stage: test
  image: node:18-alpine
  script:
    - npm install
    - npm test
  cache:
    paths:
      - node_modules/

# --- Стадия: Сборка и публикация образа ---
build_and_publish:
  stage: build
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker tag $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA $CI_REGISTRY_IMAGE:latest
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    - docker push $CI_REGISTRY_IMAGE:latest
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

# --- Стадия: Деплой на staging (автоматический) ---
deploy_staging:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache curl
  script:
    - echo "🚀 Deploying to Staging..."
    - echo "Image: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
    - echo "Environment: staging"
    - # В реальном проекте здесь был бы вызов kubectl, docker run и т.д.
    - sleep 5
    - curl -s http://localhost:3000/health || echo "⚠️ Health check skipped (no actual deployment)"
    - echo "✅ Staging deployment complete"
  environment:
    name: staging
    url: https://staging.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

# --- Стадия: Деплой на production (ручной) ---
deploy_production:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache curl
  script:
    - echo "🚀 Deploying to Production..."
    - echo "Image: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
    - echo "Environment: production"
    - echo "Version: $APP_VERSION"
    - # В реальном проекте здесь был бы вызов kubectl, docker run и т.д.
    - echo "✅ Production deployment complete"
  environment:
    name: production
    url: https://production.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  when: manual
EOF
```

#### Шаг 6. Первый коммит и проверка окружений

```bash
git add .
git commit -m "feat: add application with staging and production environments"
git push origin main
```

1. Перейдите в GitLab → **Deployments** → **Environments**.
2. Вы увидите два окружения: `staging` и `production`.
3. Нажмите на окружение `production` — должна отобразиться кнопка **"Deploy"** (ручной деплой).

### Часть 2 (2 часа) — Review Apps и динамические окружения

#### Шаг 7. Добавление Review Apps в `.gitlab-ci.yml`

Обновите файл, добавив стадию `deploy_review` и задачу для остановки Review App:

```bash
cat >> .gitlab-ci.yml << 'EOF'

# --- Стадия: Review App (для Merge Request) ---
deploy_review:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache curl
  script:
    - echo "📦 Deploying Review App for branch: $CI_COMMIT_REF_NAME"
    - echo "Image: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
    - echo "Environment URL: https://$CI_ENVIRONMENT_SLUG.example.com"
    - # В реальном проекте здесь развертывание в облаке или Kubernetes
    - sleep 3
    - echo "✅ Review App deployed"
  environment:
    name: review/$CI_COMMIT_REF_NAME
    url: https://$CI_ENVIRONMENT_SLUG.example.com
    on_stop: stop_review_app
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

# --- Задача: Остановка Review App ---
stop_review_app:
  stage: deploy
  image: alpine:latest
  script:
    - echo "🛑 Stopping Review App for branch: $CI_COMMIT_REF_NAME"
    - # Здесь удаление ресурсов
    - echo "✅ Review App stopped"
  environment:
    name: review/$CI_COMMIT_REF_NAME
    action: stop
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  when: manual
EOF
```

#### Шаг 8. Добавление защищённого окружения (Protected Environment)

Настройте защиту для production-окружения :

1. Перейдите в **Settings** → **CI/CD** → **Protected Environments**.
2. Нажмите **"Add protected environment"**.
3. Выберите `production`.
4. Установите права:
   - **Allowed to deploy:** `Maintainers` (или `Developers + Maintainers`).
5. Нажмите **"Protect"**.

#### Шаг 9. Создание Merge Request и тестирование Review App

```bash
# Создание feature-ветки
git checkout -b feature/add-version-endpoint

# Добавление нового эндпоинта
cat >> index.js << 'EOF'

app.get('/version', (req, res) => {
  res.json({ version: process.env.APP_VERSION || '1.0.0' });
});
EOF

# Коммит и push
git add index.js
git commit -m "feat: add /version endpoint"
git push origin feature/add-version-endpoint
```

1. Перейдите в GitLab → **Merge Requests** → **New merge request**.
2. Выберите `feature/add-version-endpoint` → `main`.
3. Нажмите **"Create merge request"**.
4. В MR вы увидите:
   - Статус пайплайна.
   - Ссылку **"View app"** на развернутый Review App (если настроена инфраструктура).
   - Деплой в окружение `review/feature-add-version-endpoint`.

#### Шаг 10. Настройка автоматической остановки Review App

Обновите `stop_review_app` для автоматической остановки при слиянии MR:

```yaml
stop_review_app:
  stage: deploy
  image: alpine:latest
  script:
    - echo "🛑 Stopping Review App for branch: $CI_COMMIT_REF_NAME"
    - # Здесь удаление ресурсов
    - echo "✅ Review App stopped"
  environment:
    name: review/$CI_COMMIT_REF_NAME
    action: stop
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event" && $CI_MERGE_REQUEST_APPROVED == "true"
  when: manual
```

#### Шаг 11. Добавление переменных окружения с областью видимости

Настройте переменные для разных окружений :

1. Перейдите в **Settings** → **CI/CD** → **Variables**.
2. Добавьте переменные:

| Key | Value | Environment | Protected | Masked |
|:---|:---|:---|:---|:---|
| `APP_VERSION` | `1.0.0` | `*` | ❌ | ❌ |
| `STAGING_URL` | `https://staging.example.com` | `staging` | ❌ | ❌ |
| `PRODUCTION_URL` | `https://production.example.com` | `production` | ✅ | ❌ |
| `PROD_API_KEY` | `secret-key-123` | `production` | ✅ | ✅ |

## 7. ЧАСТЫЕ ОШИБКИ И ИХ РЕШЕНИЕ

| Ошибка | Причина | Решение |
|:---|:---|:---|
| `Environment not found` | Окружение не создано | Проверьте определение `environment:` в джобе |
| Review App не появляется в MR | Неправильные `rules` | Используйте `if: $CI_PIPELINE_SOURCE == "merge_request_event"` |
| URL Review App недоступен | Не настроена инфраструктура | Настройте DNS или используйте `nip.io` для тестов  |
| Деплой в production доступен всем | Защита не настроена | Настройте Protected Environment в настройках CI/CD |
| Переменные не подставляются | Неправильная область видимости | Установите `environment:` для переменных  |
| `on_stop` не работает | Неправильное имя джобы | Убедитесь, что имя совпадает с `environment:name` в джобе остановки |
| Не удаётся остановить Review App | Окружение уже удалено | Проверьте статус окружения в GitLab → Deployments → Environments |
