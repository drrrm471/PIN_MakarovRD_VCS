## 3. ТЕОРЕТИЧЕСКОЕ ВВЕДЕНИЕ

### 3.1. Удалённые репозитории в Git

Удалённый репозиторий (remote) — это версия проекта, хранящаяся на сервере . В Git каждый локальный репозиторий может быть связан с несколькими удалёнными.

**Основные команды для работы с удалёнными репозиториями:**

| Команда | Назначение |
|:---|:---|
| `git remote -v` | Просмотр списка удалённых репозиториев |
| `git remote add <name> <url>` | Добавление удалённого репозитория |
| `git remote remove <name>` | Удаление удалённого репозитория |
| `git fetch <remote>` | Загрузка изменений из удалённого репозитория без слияния |
| `git pull <remote> <branch>` | Загрузка изменений и слияние с текущей веткой |
| `git push <remote> <branch>` | Отправка изменений в удалённый репозиторий |

### 3.2. Модель совместной разработки

В GitLab совместная работа организуется через модель **Fork + Merge Request** :

1. **Fork** — создание копии репозитория в вашем аккаунте.
2. **Clone** — клонирование форка на локальную машину.
3. **Создание ветки** — работа над новой функцией в отдельной ветке.
4. **Push** — отправка изменений в ваш форк.
5. **Merge Request** — запрос на вливание изменений в исходный репозиторий.
6. **Code Review** — обсуждение и ревью кода.
7. **Merge** — вливание изменений в целевую ветку.

### 3.3. Синхронизация форка с upstream

После создания форка важно поддерживать его актуальность:

```bash
# Добавление upstream (исходного репозитория)
git remote add upstream git@gitlab.com:original-owner/original-repo.git

# Получение изменений из upstream
git fetch upstream

# Слияние изменений в свою ветку
git checkout main
git merge upstream/main
```

## 4. ПОШАГОВАЯ ИНСТРУКЦИЯ

### Часть 1 (2 часа) — Fork, Clone и работа с несколькими remotes

#### Шаг 1. Создание базового репозитория (для преподавателя или одного из студентов)

Один студент (или преподаватель) создаёт репозиторий-источник:

1. Войдите в GitLab.
2. Нажмите **"New project"** → **"Create blank project"**.
3. Название: `collab-project`.
4. Уровень доступа: **"Public"**.
5. **Важно:** Оставьте галочку "Initialize repository with a README" — создадим файл README.md.
6. Нажмите **"Create project"**.

Создайте начальную структуру:

```bash
git clone git@gitlab.com:username/collab-project.git
cd collab-project
```

Добавьте файл `CONTRIBUTORS.md`:

```bash
echo "# Участники проекта" > CONTRIBUTORS.md
echo "" >> CONTRIBUTORS.md
echo "| Имя | Роль |" >> CONTRIBUTORS.md
echo "|-----|------|" >> CONTRIBUTORS.md
echo "| Иванов Иван | Ментор |" >> CONTRIBUTORS.md

git add CONTRIBUTORS.md
git commit -m "docs: add CONTRIBUTORS.md"
git push origin main
```

#### Шаг 2. Создание Fork каждым студентом

Каждый студент создаёт fork репозитория `collab-project`:

1. Перейдите на страницу репозитория `collab-project` на GitLab.
2. Нажмите кнопку **"Fork"** (в правом верхнем углу).
3. Выберите ваш аккаунт или группу как место для форка.
4. Нажмите **"Fork project"**.

![Fork](https://docs.gitlab.com/ee/user/project/repository/forking_workflow.html)

#### Шаг 3. Клонирование форка на локальную машину

```bash
# Клонирование вашего форка
git clone git@gitlab.com:ваш_логин/collab-project.git
cd collab-project

# Проверка удалённых репозиториев
git remote -v
# origin git@gitlab.com:ваш_логин/collab-project.git
```

#### Шаг 4. Добавление upstream

```bash
# Добавление исходного репозитория как upstream
git remote add upstream git@gitlab.com:владелец_оригинала/collab-project.git

# Проверка
git remote -v
# origin    git@gitlab.com:ваш_логин/collab-project.git (fetch)
# origin    git@gitlab.com:ваш_логин/collab-project.git (push)
# upstream  git@gitlab.com:владелец_оригинала/collab-project.git (fetch)
# upstream  git@gitlab.com:владелец_оригинала/collab-project.git (push)
```

#### Шаг 5. Создание feature-ветки и внесение изменений

```bash
# Создание ветки для новой функции
git checkout -b feature/add_contributor

# Добавление себя в список участников
echo "| Сидоров Сидор | Разработчик |" >> CONTRIBUTORS.md

# Добавление файла с описанием вклада
echo "# Мой вклад в проект" > MY_CONTRIBUTION.md
echo "Добавил себя в список участников." >> MY_CONTRIBUTION.md

# Добавление и коммит
git add CONTRIBUTORS.md MY_CONTRIBUTION.md
git commit -m "docs: add self to contributors"
```

#### Шаг 6. Отправка изменений в ваш форк

```bash
# Отправка ветки в ваш форк
git push origin feature/add_contributor
```

### Часть 2 (2 часа) — Merge Requests и Code Review

#### Шаг 7. Создание Merge Request на GitLab

1. Перейдите на страницу вашего форка на GitLab.
2. Нажмите **"Merge Requests"** → **"New merge request"**.
3. Выберите:
   - **Source branch:** `feature/add_contributor` (ваш форк)
   - **Target branch:** `main` (исходный репозиторий)
4. Нажмите **"Compare branches and continue"**.
5. Заполните описание MR:

```markdown
## Добавление участника

### Что сделано:
- Добавил себя в CONTRIBUTORS.md
- Добавил файл MY_CONTRIBUTION.md с описанием вклада

### Проверка:
- [ ] Проверить форматирование таблицы
- [ ] Убедиться, что файл не содержит ошибок

Closes #1
```

6. Нажмите **"Create merge request"**.

#### Шаг 8. Code Review (ревью кода)

1. Преподаватель (или другой студент) переходит в MR.
2. Открывает вкладку **"Changes"**.
3. Оставляет комментарии к строкам кода:

   **Комментарий 1:**
   > "Форматирование таблицы нарушено. Нужно добавить разделительную строку `|---|---|---|` для трёх колонок."

   **Комментарий 2:**
   > "Хорошо, что добавил отдельный файл. Можно было объединить с README."

4. Автор MR видит комментарии и вносит правки .

#### Шаг 9. Внесение правок по результатам ревью

```bash
# Исправление форматирования
cat CONTRIBUTORS.md
# Исправляем на правильный формат с тремя колонками
```

```bash
# Добавление и коммит исправлений
git add CONTRIBUTORS.md
git commit -m "fix: correct contributors table formatting"

# Отправка исправлений в форк
git push origin feature/add_contributor
```

**Важно:** Коммиты автоматически добавляются в существующий MR.

#### Шаг 10. Слияние Merge Request

После одобрения ревью:

1. В GitLab нажмите **"Merge"**.
2. Выберите метод слияния:
   - **"Merge commit"** — создаёт merge-коммит.
   - **"Squash commits"** — объединяет все коммиты в один.
   - **"Rebase and merge"** — выполняет rebase перед слиянием.

3. Нажмите **"Merge"**.

#### Шаг 11. Обновление локального репозитория и форка

```bash
# Переключение на main
git checkout main

# Получение изменений из upstream (исходный репозиторий)
git fetch upstream

# Слияние изменений в локальный main
git merge upstream/main

# Обновление вашего форка на GitHub/GitLab
git push origin main
```

## 5. ЗАЩИТА ВЕТКИ (PROTECTED BRANCHES)

#### Шаг 12. Настройка защиты ветки main

Преподаватель или владелец репозитория:

1. Перейдите в **Settings** → **Repository** → **Protected Branches**.
2. Нажмите **"Add protected branch"**.
3. Выберите `main`.
4. Настройте правила:
   - **Allowed to merge:** Maintainers.
   - **Allowed to push:** No one (только через Merge Request).
5. Включите **"Require approval from code owners"** (если настроено).
6. **Важно:** Требуйте успешного прохождения CI/CD перед слиянием (если настроено).

## 7. ЧАСТЫЕ ОШИБКИ И ИХ РЕШЕНИЕ

| Ошибка | Причина | Решение |
|:---|:---|:---|
| `fatal: remote origin already exists` | Уже добавлен удалённый репозиторий | Проверьте `git remote -v`, при необходимости удалите: `git remote remove origin` |
| `! [rejected] main -> main (fetch first)` | Удалённый репозиторий изменился | Выполните `git pull --rebase upstream main` |
| `Permission denied (publickey)` | SSH-ключ не добавлен в GitLab | Проверьте `ssh -T git@gitlab.com`, добавьте ключ в GitLab |
| MR не даёт слить из-за конфликтов | Изменения в целевой ветке конфликтуют | Обновите свою ветку: `git checkout feature/...`<br>`git fetch upstream`<br>`git merge upstream/main`<br>Разрешите конфликты, `git push` |
| `ERROR: Project cannot be forked` | Нет прав на форк | Проверьте настройки проекта (должен быть публичным или разрешён форк) |
