## 3. ТЕОРЕТИЧЕСКОЕ ВВЕДЕНИЕ

### 3.1. Ветки в Git

Ветка в Git — это легковесный подвижный указатель на один из коммитов . Ветка по умолчанию называется `main` (ранее `master`). При создании нового коммита указатель текущей ветки автоматически сдвигается вперёд.

**Основные команды для работы с ветками:**

| Команда | Назначение |
|:---|:---|
| `git branch` | Просмотр списка веток |
| `git branch <name>` | Создание новой ветки |
| `git checkout <name>` / `git switch <name>` | Переключение на ветку |
| `git branch -d <name>` | Удаление ветки (безопасное) |
| `git branch -D <name>` | Принудительное удаление ветки |

### 3.2. Слияние веток (`git merge`)

Слияние объединяет изменения из одной ветки в другую. Git поддерживает несколько стратегий слияния :

| Стратегия | Описание |
|:---|:---|
| **Fast-forward** | Если ветка является прямым потомком текущей, Git просто перемещает указатель вперёд. |
| **Трёхстороннее слияние (ort)** | Используется по умолчанию. Создаёт новый merge-коммит, объединяя изменения из двух веток и их общего предка . |
| **--no-ff** | Принудительно создаёт merge-коммит даже при fast-forward. |

### 3.3. Конфликты слияния

Конфликт возникает, когда в одной и той же строке файла были внесены изменения в разных ветках . Git не может автоматически определить, какой вариант выбрать, и оставляет в файле специальные маркеры :

```
<<<<<<< HEAD
изменения в текущей ветке
=======
изменения в сливаемой ветке
>>>>>>> branch-name
```

Для разрешения конфликта необходимо:
1. Вручную отредактировать файл, оставив нужные изменения.
2. Удалить маркеры конфликта (`<<<<<<<`, `=======`, `>>>>>>>`).
3. Добавить файл в индекс (`git add`).
4. Завершить слияние (`git commit`).

### 3.4. Перебазирование (`git rebase`)

Rebase переписывает историю, перенося коммиты одной ветки на вершину другой . Это позволяет получить более линейную историю, но изменяет хеши коммитов, поэтому **не рекомендуется использовать на общих ветках**.

**Преимущества rebase:** чистая, линейная история.
**Недостатки:** изменение истории, риск при совместной работе.

## 4. ПОШАГОВАЯ ИНСТРУКЦИЯ

### Часть 1 (2 часа) — Основы ветвления и слияния

#### Шаг 1. Подготовка репозитория

Убедитесь, что вы находитесь в репозитории, созданном в лабораторной работе №1:

```bash
cd ~/hello-git
git status
```

Если репозиторий потерян, склонируйте его с GitLab:

```bash
git clone git@gitlab.com:username/hello-git.git
cd hello-git
```

---

#### Шаг 2. Создание файла для экспериментов

Создайте файл `features.txt` с начальным содержимым:

```bash
echo "Основные функции приложения:" > features.txt
echo "1. Авторизация пользователя" >> features.txt
echo "2. Просмотр профиля" >> features.txt
echo "3. Редактирование профиля" >> features.txt

# Добавьте и закоммитьте
git add features.txt
git commit -m "feat: add features.txt with core features"
```

---

#### Шаг 3. Создание и переключение на новую ветку

Создайте ветку `feature/payment` и переключитесь на неё:

```bash
# Создание ветки
git branch feature/payment

# Переключение на ветку
git checkout feature/payment
# или современная команда:
git switch feature/payment

# Проверка текущей ветки
git branch
```

Ожидаемый вывод: звёздочка (`*`) должна стоять напротив `feature/payment`.

---

#### Шаг 4. Внесение изменений в новой ветке

Внесите изменения в файл `features.txt`:

```bash
# Добавляем строки в файл
echo "4. Оплата банковской картой" >> features.txt
echo "5. История платежей" >> features.txt

# Проверяем изменения
cat features.txt

# Добавляем и коммитим
git add features.txt
git commit -m "feat(payment): add payment and history features"
```

---

#### Шаг 5. Создание ещё одной ветки

Вернитесь в ветку `main` и создайте ещё одну ветку:

```bash
# Возврат в main
git checkout main

# Создание второй ветки
git checkout -b feature/notifications
# Флаг -b создаёт ветку и сразу переключается на неё
```

Внесите изменения, конфликтующие с первой веткой:

```bash
# Изменяем существующую строку (а не добавляем новую!)
echo "1. Авторизация с двухфакторной аутентификацией" > features.txt
echo "2. Просмотр профиля с аватаркой" >> features.txt
echo "3. Редактирование профиля" >> features.txt
echo "4. Система уведомлений" >> features.txt

git add features.txt
git commit -m "feat(notifications): add 2FA and notification system"
```

---

#### Шаг 6. Слияние веток (без конфликта)

Вернитесь в `main` и выполните слияние первой ветки:

```bash
git checkout main
git merge feature/payment --no-ff -m "Merge branch 'feature/payment'"
```

Так как изменения из `feature/payment` были добавлены в конец файла, конфликта не возникнет.

Просмотрите историю:

```bash
git log --oneline --graph --all
```

---

#### Шаг 7. Слияние с конфликтом

Теперь попробуйте слить вторую ветку — возникнет конфликт:

```bash
git merge feature/notifications
```

Ожидаемый вывод:

```
Auto-merging features.txt
CONFLICT (content): Merge conflict in features.txt
Automatic merge failed; fix conflicts and then commit the result.
```

---

#### Шаг 8. Разрешение конфликта вручную

Посмотрите состояние и конфликтный файл:

```bash
git status
cat features.txt
```

Содержимое `features.txt` будет содержать маркеры конфликта:

```
<<<<<<< HEAD
Основные функции приложения:
1. Авторизация пользователя
2. Просмотр профиля
3. Редактирование профиля
4. Оплата банковской картой
5. История платежей
=======
1. Авторизация с двухфакторной аутентификацией
2. Просмотр профиля с аватаркой
3. Редактирование профиля
4. Система уведомлений
>>>>>>> feature/notifications
```

**Разрешите конфликт**, оставив нужные изменения. Например, объединённый вариант:

```
Основные функции приложения:
1. Авторизация с двухфакторной аутентификацией
2. Просмотр профиля с аватаркой
3. Редактирование профиля
4. Оплата банковской картой
5. История платежей
6. Система уведомлений
```

После редактирования:

```bash
# Добавляем разрешённый файл
git add features.txt

# Завершаем слияние
git commit -m "merge: resolve conflict between payment and notifications"

# Проверяем историю
git log --oneline --graph --all
```

---

#### Шаг 9. Использование VS Code для разрешения конфликтов (опционально)

Откройте проект в VS Code:

```bash
code ~/hello-git
```

Если вы находитесь в состоянии конфликта, VS Code подсветит проблемные файлы. В редакторе доступны кнопки:
- **Accept Current Change** — оставить изменения из текущей ветки.
- **Accept Incoming Change** — оставить изменения из сливаемой ветки.
- **Accept Both Changes** — оставить оба варианта.
- **Compare Changes** — сравнить изменения.

### Часть 2 (2 часа) — Rebasing и работа с GitLab

#### Шаг 10. Создание ситуации для rebase

Создайте новую ветку от `main`:

```bash
git checkout main
git checkout -b feature/database
```

Внесите изменения:

```bash
echo "database: SQLite" > config.txt
echo "database: PostgreSQL" >> config.txt

git add config.txt
git commit -m "feat(db): add database configuration"
```

Вернитесь в `main` и создайте конфликтующий коммит:

```bash
git checkout main
echo "database: MySQL" > config.txt
git add config.txt
git commit -m "fix(db): change default database to MySQL"
```

---

#### Шаг 11. Перебазирование (rebase)

Переключитесь на ветку `feature/database` и выполните rebase на `main`:

```bash
git checkout feature/database
git rebase main
```

Возникнет конфликт, так как обе ветки изменили файл `config.txt`.

Разрешите конфликт аналогично шагу 8, затем:

```bash
# После редактирования файла
git add config.txt

# Продолжить rebase
git rebase --continue
```

**Если нужно прервать rebase:**
```bash
git rebase --abort
```

---

#### Шаг 12. Сравнение merge и rebase

Просмотрите историю:

```bash
git log --oneline --graph --all
```

Обратите внимание, что после rebase история стала линейной — коммиты из `feature/database` перенесены поверх `main` без создания merge-коммита .

---

#### Шаг 13. Отправка изменений в GitLab

Отправьте все ветки и теги в удалённый репозиторий:

```bash
# Отправка всех веток
git push --all origin

# Если были созданы теги
git push --tags origin
```

Создайте Merge Request на GitLab:
1. Перейдите в ваш репозиторий на GitLab.
2. Нажмите **"Merge Requests"** → **"New merge request"**.
3. Выберите исходную ветку (`feature/database`) и целевую (`main`).
4. Добавьте описание и создайте MR.
5. Проверьте, что CI/CD (если настроен) проходит успешно.
6. Выполните слияние через интерфейс GitLab.

---

#### Шаг 14. Создание ветки release (практика Git Flow)

```bash
# От main создаём релизную ветку
git checkout main
git checkout -b release/v1.0

# Вносим финальные правки
echo "version: 1.0.0" > version.txt
git add version.txt
git commit -m "chore(release): bump version to 1.0.0"

# Отправляем релизную ветку
git push origin release/v1.0
```

На GitLab создайте Merge Request из `release/v1.0` в `main` с пометкой "Release v1.0.0".

## 6. ЧАСТЫЕ ОШИБКИ И ИХ РЕШЕНИЕ

| Ошибка | Причина | Решение |
|:---|:---|:---|
| `You have unmerged paths`  | Не все конфликты разрешены | Проверьте `git status`, разрешите конфликты, выполните `git add` и `git commit` |
| `fatal: Not possible to fast-forward, aborting` | Конфликт при fast-forward | Используйте `git merge --no-ff` или разрешите конфликт вручную |
| `error: cannot rebase: You have unstaged changes` | Есть незакоммиченные изменения | Выполните `git stash` перед rebase или закоммитьте изменения |
| После `git push` ошибка `[rejected]` | Удалённая ветка изменилась | Выполните `git pull --rebase` перед push  |
| `git mergetool` не запускается | Утилита не установлена | `sudo apt install meld` или используйте ручное разрешение  |
